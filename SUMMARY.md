# Results: Boa and Porffor, synchronous P2

**JS-side Canonical ABI conversion is not an inherent size or performance win.** Boa benefits strongly from native B/C conversion. On Porffor, a tuned A can match B's scalar-call speed and beat B/C on import loops, while B remains substantially smaller and faster on byte lists. C's generic boundary adds a measurable fixed cost, but does not make it slower for every payload.

These are real components with identical WIT and application JS. All six primary builds and three diagnostic variants passed the same correctness suite, in all three independent process runs. Exact sources, tool versions and scope are in [README.md](README.md), [PORTING.md](docs/PORTING.md), and [upstream.lock.json](upstream.lock.json). The original request is in [PROMPT.md](PROMPT.md).

## Approaches and call paths

| Approach | Mechanism | Benefits | Drawbacks |
|---|---|---|---|
| A: js-guest-bindgen | Native core wrapper → generated JS canonical conversion → app | Small engine contract; portable JS bindings; Porffor can optimize direct import paths | Boa interprets binding work; generated logging/helpers can dominate; AOT can expand helper code |
| B: specialized native | Generated native ABI runtime → interface-specific native engine shim → app | Static specialization and dead-code removal; smallest Porffor build | Per-world native shims/builds; additional backend work |
| C: wit-dylib | WIT-specific generated Wasm → generic native push/pop engine adapter → app | Uniform interpreter integration; potential prebuilt engine reuse | Generic call state and callbacks; shared-library/PIC packaging costs |

B/C reuse componentize-js's actual engine-independent generator; its mozjs runtime is replaced with Boa/Porffor adapters. B's Canonical ABI backend is generated by wit-bindgen-c. Its shims only box/unbox typed native values; canonical offsets, flattening and return areas stay in the runtime. C uses real wit-dylib 0.254.0, matching componentize-js's dependency. **wit-dylib already generates WIT-specific native ABI code**; its generality is chiefly the engine-facing callback contract, not interpreting WIT on every call.

| Boa | C | 9,461,450 | 2,375,676 |
| Porffor | A | 859,053 | 243,203 |
| Porffor | B | 398,448 | 124,417 |
| Porffor | C | 1,050,847 | 439,302 |

Boa A is only **1.4% smaller than B**. Porffor B is **53.6% smaller than A**. C is **28.8% larger than B on Boa**, and **163.7% larger on Porffor**.

Those C deltas are **not the size of generic lifting/lowering alone**: the generated world library is only **6,611 bytes** before stripping. Shared libc, PIC engine code, linking scaffolding and reduced static elimination account for much of the deployment difference. C's separate stripped engine libraries are about 8.57 MB for Boa and 0.36 MB for Porffor; [sizes.json](results/sizes.json) and the section breakdowns preserve the details. Engine sharing across components was not measured.

C's scalar cost over B is about **0.53 µs on Boa** and **0.18 µs on Porffor**. That is substantial proportionally for an almost-empty call, but small absolutely. Several larger-payload ranges overlap. C was faster than B for Porffor's 1 KiB string case, so specialization does not establish a universal throughput win.

### Controls: why the default A numbers are not the whole answer

A's generated bindings invoke inactive debug logging with allocated argument objects. Porffor A also uses JS UTF-8 routines. These controls remove only the debug statements, then optionally replace UTF-8 intrinsics with native routines; canonical layout work still remains in generated JS.

| A variant | Stripped bytes | Scalar µs | String 1 KiB µs | Bytes 1 KiB µs | 100 imports µs |
|---|---:|---:|---:|---:|---:|
| Boa, no logging | 7,236,987 | 2.107 | 41.522 | 33.315 | 838.532 |
| Porffor, no logging | 754,944 | 0.240 | 469.746 | 2.606 | 10.854 |
| Porffor, no logging + native UTF-8 | 705,438 | 0.242 | 5.372 | 2.633 | 11.430 |

This makes the architectural distinction clearer. Boa still pays for interpreted binding work after logging removal. Porffor compiles the bindings to Wasm: tuned A's scalar range overlaps B, and its import loop is consistently faster than B/C in these runs. Native UTF-8 removes most of the string gap. B/C still beat tuned A on byte lists; B is about **43.5% smaller** than tuned Porffor A. Thus A can offer a real fixed-call/import advantage over C on an AOT engine, but neither its speed nor its size advantage holds across workloads or against B.

## Decision and limits

For **Boa**, B/C are the stronger performance starting point; A's modest saving over B does not compensate for interpreted conversion in this workload. For **Porffor**, B is the size-oriented starting point, while A with logging removed and native text intrinsics deserves consideration for frequent small imports. Choose C for its uniform integration contract and potential engine reuse, rather than assuming its measured deployment overhead is negligible. These C artifacts embed the app, so that reuse benefit is architectural; Porffor's per-app compilation also weakens it.

The scope is u32, f64, UTF-8 strings, byte lists, one mixed record, and synchronous imports. B's shims are explicit for this world, and unimplemented C type callbacks trap. Resources, variants, 64-bit values, promises/I/O, arbitrary-WIT shim generation, and malformed-JS validation parity are not demonstrated. Both engines copy buffers. Runs used one pinned CPU on a shared x86-64 host; small differences and overlapping ranges should not be treated as statistically established wins. The experiment establishes practical costs for these concrete implementations, not an intrinsic ranking of every possible A/B/C implementation.
